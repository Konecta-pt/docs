<Info>
Verificado contra a API da Cloudflare a 28/07/2026. As tabelas distinguem o que o
**código precisa** do que está **configurado em produção** — não é a mesma lista.
</Info>

Os segredos **nunca** entram no `wrangler.toml` nem no repositório. Só as variáveis
não sensíveis (`[vars]`) ficam versionadas.

| Onde corre | Como se configura |
| --- | --- |
| Workers | `wrangler secret put NOME` (produção) · `wrangler secret put NOME --env development` (dev) |
| Pages (admin, site, checkout) | dashboard Cloudflare → o projeto → Settings → Environment variables, com **Production** e **Preview** separados |
| GitHub Actions | Settings → Secrets → Actions (`CLOUDFLARE_API_TOKEN`) |

<Warning>
Não há herança entre ambientes. Um `wrangler secret put X` sem `--env development`
existe **só em produção**; o worker de dev arranca sem ele e falha na primeira
chamada que dependa dele. Repetir sempre o comando para cada ambiente.
</Warning>

## API-BACKEND (`konecta-api`)

**Secrets configurados:** `SUPABASE_URL`, `SUPABASE_ANON_KEY`,
`SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_JWT_SECRET`, `JWT_SECRET`,
`STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, `RESEND_API_KEY`,
`INTERNAL_API_SECRET`, `INTERNAL_WEBHOOK_SECRET`.

O `SUPABASE_JWT_SECRET` é o que permite ao `authMiddleware` aceitar tokens emitidos
pelo Supabase (HS256), além dos tokens próprios.

**Referidos no código mas não configurados:**

| Variável | Consequência de estar em falta |
| --- | --- |
| `UPSTASH_REDIS_URL` · `UPSTASH_REDIS_TOKEN` | **o rate limiting está desligado** (ver abaixo) |
| `DATABASE_URL` | declarado no `types/env.ts`, sem uso real — o acesso é pelo cliente Supabase |
| `STRIPE_WEBHOOK_SECRET` | nenhuma — este worker não recebe webhooks da Stripe (ver [API-BACKEND](/repos/api-backend)) |

<Warning>
O `rateLimiter()` faz `return next()` sem limitar nada quando o Upstash não está
configurado. Como não está, **não há rate limiting em produção** — as variáveis
`RATE_LIMIT_REQUESTS=100` e `RATE_LIMIT_WINDOW_SECONDS=60` estão lá a sugerir um
limite que não existe. Falha em aberto, não fechado.
</Warning>

**Variáveis (`[vars]`, versionadas):**

| Variável | Produção | O que faz |
| --- | --- | --- |
| `JWT_EXPIRY_HOURS` | `2` | validade do access token |
| `REFRESH_TOKEN_EXPIRY_DAYS` | `30` | validade do refresh token |
| `RATE_LIMIT_REQUESTS` / `RATE_LIMIT_WINDOW_SECONDS` | `100` / `60` | limite por janela |
| `CORS_ORIGINS` | konecta.pt, www, app, pay, admin, konecta-admin.pages.dev | origens do browser aceites |
| `CHECKOUT_FRONTEND_URL` | `https://pay.konecta.pt` | para onde vai o checkout |
| `ESIM_SERVICE_URL` / `PAYMENT_SERVICE_URL` | `eu-esims` / `payments` | serviços internos |

**Bindings:** `SESSIONS_KV`, `CACHE_KV`. `[placement] mode = "smart"`.

## API-ESIMS (`konecta-esims`)

**Secrets configurados:** `SUPABASE_URL`, `SUPABASE_ANON_KEY`,
`SUPABASE_SERVICE_ROLE_KEY`, `INTERNAL_API_SECRET`, `SYNC_SECRET`, `ESIMCARD_TOKEN`,
`CMLINK_EMAIL`, `CMLINK_PASSWORD`, `TWOCAPTCHA_KEY`.

**Variáveis:** `ENV`, `DEFAULT_PROVIDER` (`esimcard`).

**Bindings:** `CACHE_KV`, `CMLINK_SESSION`, `CMLINK_PRICES`, `CMLINK_ORDERS`,
`BROWSER` (Browser Rendering).

O `ESIMCARD_TOKEN` é o caminho em uso; o `ESIMCARD_EMAIL`/`ESIMCARD_PASSWORD` (login
dinâmico) existem no código mas **não estão configurados** e não fazem falta
enquanto o token for válido.

<Warning>
O secret `ESIMACCESS_ACCESS_CODE` continua configurado neste worker, apesar de o
provider ter sido removido do código. Apagar com
`wrangler secret delete ESIMACCESS_ACCESS_CODE`.
</Warning>

## API-PAYMENTS (`konecta-payments`)

**Secrets configurados:** `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`,
`STRIPE_WEBHOOK_SECRET`, `INTERNAL_WEBHOOK_SECRET`.

**Variáveis:** `BACKEND_API_URL` (`https://api.konecta.pt`),
`WEBHOOK_CALLBACK_URL`, `CORS_ORIGINS`.

**Não configurados:** `APPLE_PAY_MERCHANT_ID`, `APPLE_PAY_DOMAIN` — declarados no
tipo `Env` mas ausentes, portanto o Apple Pay não está operacional por esta via.

O `BACKEND_API_URL` não é decorativo: é de lá que este worker vai buscar o preço
verdadeiro da encomenda. Ver [API-PAYMENTS](/repos/api-payments).

## Projetos Pages

Configurados no dashboard Cloudflare, por projeto, com ambientes **Production** e
**Preview** separados.

### konecta-admin (`admin.konecta.pt`)

Duas famílias, e a distinção é a coisa mais importante desta página.

**Configurado em produção:** `CF_ACCESS_AUD`, `ADMIN_EMAILS`, `STRIPE_SECRET_KEY`,
`ESIMS_SYNC_SECRET`, `ESIMS_SYNC_URL`, `CLOUDFLARE_API_TOKEN`, `VITE_API_URL`,
`VITE_INTERNAL_API_SECRET`, `VITE_SUPABASE_SERVICE_ROLE_KEY`, `VITE_PAGESPEED_KEY`.

`CF_ACCESS_TEAM_DOMAIN`, `ALLOWED_ORIGIN` e `ALLOWED_EMAIL_DOMAIN` não estão
definidos e usam os valores por omissão do código
(`konectapt.cloudflareaccess.com`, `https://admin.konecta.pt`).

<Warning>
**`RESEND_API_KEY` não está configurada.** O `POST /api/v1/admin/email/send` devolve
`503 RESEND_API_KEY não configurada` — o envio de emails a partir do dashboard não
funciona.
</Warning>

<Warning>
O prefixo `VITE_` significa **compilado para dentro do JavaScript que o browser
descarrega**. Não é uma variável de servidor. Neste momento a service role key do
Supabase e o segredo interno dos workers estão os dois lá. Há também um
`CLOUDFLARE_API_TOKEN` guardado neste projeto que o código das Pages Functions não
usa — se não for preciso, remover.
</Warning>

### konecta-pt (`konecta.pt`)

Só três variáveis: `VITE_API_URL`, `VITE_SUPABASE_URL` e
`VITE_SUPABASE_PUBLISHABLE_KEY`. Tudo o resto (`VITE_VAT_RATE`, `VITE_ESIMS_URL`,
`VITE_TRACK_URL`) corre com os valores por omissão do código.

<Warning>
Duas destas variáveis estão gravadas com um **tab no fim do nome** —
`VITE_API_URL\t` e `VITE_SUPABASE_URL\t`. O Vite procura `VITE_API_URL` exato, por
isso o código lê `undefined` e cai no fallback. Reescrever os nomes no dashboard.
</Warning>

### payments-konecta-web (`pay.konecta.pt`)

`NEXT_PUBLIC_API_URL` e `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`.

<Warning>
**Nenhum dos três projetos tem variáveis no ambiente Preview.** Os previews de
`dev` arrancam sem configuração nenhuma — é preciso duplicar as variáveis de
Production para Preview antes de os usar como ambiente de teste. Ver
[Ambientes de teste](/ambientes-teste).
</Warning>

## Segredos partilhados entre serviços

| Segredo | Quem tem de ter o mesmo valor |
| --- | --- |
| `INTERNAL_API_SECRET` | API-BACKEND, API-ESIMS, e `VITE_INTERNAL_API_SECRET` no build do admin |
| `INTERNAL_WEBHOOK_SECRET` | API-PAYMENTS → API-BACKEND (header `X-Webhook-Secret`) |
| `SYNC_SECRET` | API-ESIMS ↔ `ESIMS_SYNC_SECRET` nas Pages Functions do admin |
| `STRIPE_WEBHOOK_SECRET` | API-PAYMENTS ↔ endpoint registado no Stripe |

<Warning>
Rodar um destes obriga a atualizar **todos** os consumidores ao mesmo tempo. Meio
rodado parte o fulfillment: o backend deixa de conseguir gerar eSIMs e as encomendas
ficam pagas por entregar.
</Warning>

## Comandos

```bash theme={null}
wrangler secret put NOME                      # produção
wrangler secret put NOME --env development    # ambiente de testes
wrangler secret list                          # ver os nomes (nunca os valores)
wrangler secret list --env development
wrangler secret delete NOME
```

O `wrangler` pede o valor de forma interativa — não fica no histórico do shell.
Nenhum comando mostra o valor de um secret depois de gravado: se o perdeste,
gera-se um novo.
