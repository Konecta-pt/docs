## Modelo de branches

Todos os repositórios usam **só duas branches**:

- **`main` = produção**
- **`dev` = teste / integração**

Não há branches `feat/*` de longa duração nem `develop` — tudo o que é trabalho em
curso vive em `dev` até estar pronto para ir para produção via PR.

## Fluxo diário da equipa

1. Trabalhar sempre a partir de `dev` (`git checkout dev && git pull`).
2. Fazer commit e `git push origin dev`.
3. Abrir **PR `dev → main`** no GitHub.
4. O **CI (`typecheck`)** corre automaticamente no PR — instala dependências e
   corre `tsc`/build. Sem check verde, não é possível fazer merge.
5. Merge do PR para `main` → **deploy automático** para produção (ver abaixo,
   varia por tipo de repo).

<Info>
Cada repo tem `.github/workflows/ci.yml`, que corre em PRs para `main` e falha o
check se o typecheck não passar.
</Info>

## Proteção do `main`

Configurado via GitHub *Settings → Branches → Add branch protection rule*:

- **Branch name pattern:** `main`
- **Require a pull request before merging** — push direto para `main` fica bloqueado.
- **Require status checks to pass** → check `typecheck`.
- **Do not allow bypassing the above settings** — nem admins passam por cima das regras.

<Note>
O GitHub tem duas formas de proteger branches: **Rulesets** (Settings → Rules →
Rulesets) e **Branch protection rules** (Settings → Branches), que é a usada aqui.
Rulesets exigem o plano **GitHub Team** (pago); Branch protection rules têm o
mesmo efeito prático (PR obrigatório + CI obrigatório + sem bypass) e funcionam
no **plano gratuito**.
</Note>

## Como cada tipo de repo deploya

### Cloudflare Workers (API-BACKEND, API-ESIMS, API-PAYMENTS)
**Deploy automático** via GitHub Actions, com **um workflow por ambiente**:

| Ficheiro | Branch | Comando | Vai para |
| --- | --- | --- | --- |
| `.github/workflows/deploy-dev.yml` | `dev` | `wrangler deploy --env development` | `*-dev.konecta.pt` |
| `.github/workflows/deploy-prod.yml` | `main` | `wrangler deploy` | domínio de produção |

- Ambos têm `paths: ['workers/**']` — só disparam se o commit tocar código do worker.
- Ambos correm `typecheck` primeiro e o job de deploy tem `needs: typecheck`, por
  isso um erro de tipos bloqueia o ambiente respetivo.
- Autenticam-se com o secret `CLOUDFLARE_API_TOKEN` configurado no GitHub Actions.
- Também podem ser disparados manualmente (`workflow_dispatch`) a partir do
  separador Actions no GitHub, sem precisar de push.

### Quando o deploy falha e o typecheck passa

O `typecheck` corre num job separado, por isso um run pode ficar "meio vermelho"
com o `wrangler` a nunca publicar nada. Três causas já encontradas, por ordem em
que aparecem (cada uma só se vê depois de resolver a anterior):

<AccordionGroup>
<Accordion title="In a non-interactive environment, it's necessary to set a CLOUDFLARE_API_TOKEN">
O secret não existe, **ou existe no sítio errado**. Um secret criado em
`Settings → Environments → <ambiente> → Secrets` é um **environment secret**: só
é visível a um job que declare `environment: <nome>`. Os `deploy-*.yml` não
declaram nenhum, por isso `${{ secrets.CLOUDFLARE_API_TOKEN }}` fica **string
vazia** e o wrangler comporta-se como se não houvesse token.

Tem de ser um **repository secret**: `Settings → Secrets and variables → Actions
→ New repository secret`.
</Accordion>

<Accordion title="A request to the Cloudflare API (/memberships) failed — code 10000">
Sem `account_id`, o wrangler chama `GET /memberships` para descobrir a que conta
pertence o token — e um API token de deploy normal **não tem permissão nesse
endpoint** (só a Global API Key, ou um token com `User → Memberships: Read`).

Resolve-se fixando a conta no `wrangler.toml` (já está nos três repos, a seguir
ao `name`), o que também torna o deploy local determinístico:

```toml
account_id = "719720bab62cc014f5f5b43894c33e7a"
```

O account ID não é sensível — aparece no URL do dashboard.
</Accordion>

<Accordion title="A request to the Cloudflare API (/accounts/.../workers/services/...) failed — code 10000">
Agora a conta está certa e o problema é o **token não ter Workers nessa conta**.
Cria-o em `dash.cloudflare.com/profile/api-tokens` a partir do template **Edit
Cloudflare Workers**, e confirma que em **Account Resources** está incluída a
conta `Konecta.pt@gmail.com's Account` — um token limitado a outra conta, ou só
com permissões de zona, dá exatamente este erro.

Permissões mínimas: `Workers Scripts: Edit`, `Workers KV Storage: Edit`,
`Account Settings: Read` e, para os custom domains `*-dev.konecta.pt`,
`Workers Routes: Edit` + `Zone: Read` na zona `konecta.pt`.

Para confirmar um token antes de o colar no GitHub:

```bash
curl -s https://api.cloudflare.com/client/v4/user/tokens/verify \
  -H "Authorization: Bearer <token>"

curl -s https://api.cloudflare.com/client/v4/accounts/719720bab62cc014f5f5b43894c33e7a/workers/scripts \
  -H "Authorization: Bearer <token>"
```

O primeiro diz se o token é válido; o segundo é o que o wrangler precisa mesmo —
se der `10000`, faltam as permissões de Workers.
</Accordion>
</AccordionGroup>

<Warning>
Até 29/07/2026 o GitHub Actions **nunca publicou nada** — todos os deploys que
existem foram `wrangler deploy` manual a partir da máquina local. Não assumas que
um worker está atualizado só porque o push passou.
</Warning>

<Note>
O `ci.yml` é outra coisa e continua a fazer falta: corre nos **pull requests** para
`main` e é o check que a branch protection exige antes do merge. Os `deploy-*.yml`
correm depois, no push.
</Note>

Deploy manual local (só para emergências / debugging, fora do fluxo normal —
exige `wrangler login`):

```bash theme={null}
cd <repo>/workers
wrangler deploy                    # produção
wrangler deploy --env development  # ambiente de teste
```

- Secrets por ambiente: `wrangler secret put NOME [--env development]`.
- Crons e rotas são definidos no `wrangler.toml`. Atenção: os ambientes **não
  herdam** `vars`, `kv_namespaces`, `routes` nem `browser` do bloco de topo, mas
  **herdam** `triggers` — por isso o API-ESIMS declara `crons = []` em
  `[env.development.triggers]`, para o dev não duplicar os crons de produção.

### Cloudflare Pages (admin-dashboard, konecta.pt, payments-konecta-web)
Build automático por push, gerido pela integração nativa Cloudflare Pages ↔ GitHub
(não passa pelo GitHub Actions):

- **Production branch = `main`** → domínio de produção.
- Qualquer outra branch (ex.: `dev`) → **preview deployment** com URL próprio (ambiente de teste).
- Variáveis de ambiente separadas: **Production** vs **Preview**.

### Railway (LB e fallbacks)
Deploy por push do repo conectado. Variáveis de ambiente no painel Railway.

## Comandos úteis de referência rápida

```bash
# começar trabalho novo
git checkout dev
git pull origin dev

# publicar trabalho
git add <ficheiros>
git commit -m "mensagem"
git push origin dev

# depois do PR aprovado e com CI verde, o merge é feito no GitHub (botão),
# não localmente

# manter dev atualizada depois de um merge para main
git checkout dev
git pull origin dev
git merge main
git push origin dev

# disparar deploy manual de um Worker sem push (workflow_dispatch)
# GitHub → repo → Actions → "Deploy Konecta ... Worker" → Run workflow
```

## Secrets partilhados importantes

O inventário completo, serviço a serviço, está em [Secrets & variáveis](/secrets).
Os que partem coisas quando ficam dessincronizados:

- `INTERNAL_API_SECRET` — segredo partilhado entre **API-BACKEND** e **API-ESIMS**
  (o backend chama o worker de eSIMs com `Authorization: Bearer <secret>`). No
  admin, o equivalente é `VITE_INTERNAL_API_SECRET` (tem de ser **igual**).
- `SYNC_SECRET` (API-ESIMS) ↔ `ESIMS_SYNC_SECRET` (Pages Functions do admin).
- `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`.
- `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `RESEND_API_KEY`.
- `CLOUDFLARE_API_TOKEN` — usado pelo GitHub Actions para fazer `wrangler deploy`
  nos 3 repos de Workers (configurado como secret do repositório no GitHub, não
  do Cloudflare).

<Warning>
Se rodares o `INTERNAL_API_SECRET`, tens de o atualizar em **todos** os
consumidores (worker de eSIMs, API-BACKEND e admin Pages) ou partes o fulfillment.
</Warning>

## Verificar builds localmente

- Workers: `npx tsc --noEmit` (ou o script `typecheck`).
- Admin/site: **`tsc -b`** (o build de produção usa isto — mais estrito que `tsc --noEmit`).
