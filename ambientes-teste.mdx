## O que é o ambiente de dev?

É uma **cópia do serviço a correr num URL diferente do de produção**, onde podes
testar alterações sem afetar utilizadores reais nem dados de produção.

Todos os repos do Konecta têm exatamente dois ambientes: **produção** (branch
`main`) e **dev/teste** (branch `dev`). Não há `staging` nem `feat/*` — tudo o
que é trabalho em curso vive em `dev` até estar pronto para ir para produção
via PR.

## URLs de cada serviço

Cada API de dev tem **dois endereços, de propósito diferente**:

| Serviço | Produção | Dev — humanos (com Access) | Dev — worker→worker |
|---|---|---|---|
| API-BACKEND | `api.konecta.pt` | `api-dev.konecta.pt` | `konecta-api-dev.konecta-pt.workers.dev` |
| API-ESIMS | `eu-esims.konecta.pt` | `eu-esims-dev.konecta.pt` | `konecta-esims-dev.konecta-pt.workers.dev` |
| API-PAYMENTS | `payments.konecta.pt` | `payments-dev.konecta.pt` | `konecta-payments-dev.konecta-pt.workers.dev` |
| admin-dashboard | `admin.konecta.pt` | `dev.konecta-admin.pages.dev` | — |
| konecta.pt (site) | `konecta.pt` | `dev.konecta-global-connect.pages.dev` | — |
| payments-konecta-web | `pay.konecta.pt` | `dev.payments-konecta-web.pages.dev` | — |

### Porquê dois endereços

O Cloudflare Access protege **hostnames da zona `konecta.pt`**. Isso dá-te o portal
de login em `api-dev.konecta.pt` quando abres o URL no browser — mas o Access
responde a *qualquer* pedido sem cookie de sessão com um redirect para o login,
incluindo os que vêm de outro Worker.

Por isso os workers de dev falam entre si pelos URLs `*.workers.dev`, que ficam fora
do alcance do Access e continuam protegidos pelo `INTERNAL_API_SECRET` — exatamente
o que o [LB](/repos/load-balancer) já faz em produção. É por isso que o
`ESIM_SERVICE_URL` do `konecta-api-dev` aponta para `workers.dev` e não para
`eu-esims-dev.konecta.pt`.

<Warning>
Pela mesma razão, um frontend de dev que chame a API a partir do browser tem de usar
o URL **`workers.dev`**. Se apontares o `VITE_API_URL` do preview para
`api-dev.konecta.pt`, cada `fetch` leva um 302 para a página de login e falha no
CORS.
</Warning>

<Note>
Os nomes dos projetos Pages são `konecta-admin`, `konecta-pt` e
`payments-konecta-web`. O do site tem o domínio `pages.dev` herdado de um nome
antigo — `konecta-global-connect.pages.dev` — e é esse que aparece nos URLs de
preview, não `konecta-pt`.
</Note>

## Workflow diário — passo a passo

Cenário: queres fazer uma alteração num destes 6 repos, testá-la, e depois
mandá-la para produção.

1. **Trabalha sempre a partir do branch `dev`** — nunca diretamente em `main`.
   ```bash
   git checkout dev
   git pull origin dev
   ```
2. Faz as tuas alterações normalmente (código, ficheiros, etc.).
3. Faz commit e push para `dev`:
   ```bash
   git add .
   git commit -m "descrição da alteração"
   git push origin dev
   ```
4. O deploy para dev é **automático em todos os repos**:
   - **Pages** (admin-dashboard, konecta.pt, payments-konecta-web) — a Cloudflare
     cria o preview em `dev.<projeto>.pages.dev`.
   - **Workers** (API-BACKEND, API-ESIMS, API-PAYMENTS) — o
     `deploy-dev.yml` corre em `dev` e faz `wrangler deploy --env development`.
5. Testa a tua alteração no URL de dev correspondente (tabela acima).
6. Quando estiver tudo a funcionar como esperado, abre um PR `dev → main` no
   GitHub (ver comando abaixo).
7. O CI (`typecheck`) corre automaticamente no PR. Sem check verde, o GitHub
   não deixa fazer merge (branch protection no `main`).
8. Depois de aprovado e com CI verde, faz merge do PR. Isso dispara o
   **deploy automático para produção** (GitHub Actions nos Workers; build
   nativo da Cloudflare nas Pages).

<Note>
Cada ambiente tem o seu workflow: `deploy-dev.yml` corre no push para `dev` e faz
`wrangler deploy --env development`; `deploy-prod.yml` corre no push para `main` e
faz `wrangler deploy`. Nos dois, o job de deploy só arranca depois de o `typecheck`
passar — um erro de tipos impede tanto o dev como a produção.
</Note>

## Comandos de referência

```bash
# Trabalhar no branch dev
git checkout dev
git pull origin dev

# Commit e push para dev
git add .
git commit -m "descrição da alteração"
git push origin dev

# O deploy de dev é automático no push para `dev`. Estes comandos são só para
# emergência ou para o primeiro arranque, e exigem `wrangler login`.
cd workers
wrangler deploy --env development   # ambiente de testes
wrangler deploy                     # produção

# Adicionar/atualizar um secret no ambiente de testes
wrangler secret put NOME_SECRET --env development

# Adicionar/atualizar um secret em produção
wrangler secret put NOME_SECRET

# Ver secrets configurados no ambiente de testes
wrangler secret list --env development

# Ver logs em tempo real do ambiente de testes
wrangler tail --env development

# Abrir PR de dev → main quando estiver pronto
gh pr create --base main --head dev --title "descrição" --body "o que muda"

# Manter dev atualizada depois de um merge para main
git checkout dev
git pull origin dev
git merge main
git push origin dev
```

## Secrets no ambiente de dev

Os secrets (`SUPABASE_SERVICE_ROLE_KEY`, `STRIPE_SECRET_KEY`, etc.) **nunca
vão para o `wrangler.toml`** — só variáveis não sensíveis (`[vars]`) ficam lá.
Cada ambiente (produção e dev) tem os seus próprios secrets, configurados
separadamente via CLI, e **não há herança automática** entre eles.

Isto significa que, ao criares um worker de dev pela primeira vez (ou ao
adicionar um secret novo), tens de o configurar explicitamente em dev também:

```bash
cd API-BACKEND/workers
wrangler secret put SUPABASE_SERVICE_ROLE_KEY --env development
# o wrangler pede o valor de forma segura (não fica no histórico do shell)
```

<Warning>
Um secret criado com `wrangler secret put NOME_SECRET` (sem `--env`) só existe
em **produção**. Se o worker de dev depender desse secret e ele não estiver
também em `--env development`, o worker de dev vai falhar a arrancar ou a
autenticar-se — repete sempre o comando com `--env development`.
</Warning>

## Pages vs. Workers — a diferença mais importante

| | Push para `dev` | Quem publica |
|---|---|---|
| **Pages** (admin-dashboard, konecta.pt, payments-konecta-web) | preview em `dev.<projeto>.pages.dev` | integração nativa Cloudflare ↔ GitHub |
| **Workers** (API-BACKEND, API-ESIMS, API-PAYMENTS) | `--env development` | GitHub Actions (`deploy-dev.yml`) |

A diferença que resta é **onde** falha quando falha: nas Pages, o build aparece no
dashboard Cloudflare; nos Workers, no separador Actions do GitHub. Um erro de
typecheck bloqueia o deploy de dev dos Workers da mesma forma que bloqueia o de
produção.
